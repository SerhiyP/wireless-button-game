# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

A wireless button game system built on Arduino Nano + nRF24L01 2.4GHz radio. Up to
`NUM_PLAYERS` button devices race to transmit a press to a central display receiver. The
first press wins; the display shows the winning player's number on a 7-segment digit,
confirms to the winning button, and controls round reset.

Players are identified by **number**, not colour (colours were removed in `acc6ff9`).

The codebase is two Arduino sketches:
- **`button/button.ino`** — single configurable firmware uploaded to every button Nano
- **`display/display.ino`** — firmware for the central receiver/display Nano

## Building & Uploading

The Arduino IDE is the normal workflow, but the IDE **does** bundle an `arduino-cli` that
compiles from the terminal — useful for verifying changes without touching hardware:

```bash
CLI="/Applications/Arduino IDE.app/Contents/Resources/app/lib/backend/resources/arduino-cli"
"$CLI" compile -b arduino:avr:nano --libraries ~/Documents/Arduino/libraries button
"$CLI" compile -b arduino:avr:nano --libraries ~/Documents/Arduino/libraries display
```

This compiles only — it does not need a board attached and never uploads. Always run it
after editing a sketch; there are no tests.

**Prerequisites:** Arduino IDE, and the RF24 library (Library Manager → "RF24"), installed
at `~/Documents/Arduino/libraries/RF24`.

**Uploading button.ino:** set `BUTTON_ID` at the top of the file to the player number
(`0`..`NUM_PLAYERS - 1`) before uploading. Everything else — radio address, the value sent
on press, the win message, the ping message — is derived from it via token pasting. Each
physical button must get a unique `BUTTON_ID`, or two buttons will share a radio address.

**Debugging:** Serial Monitor at **9600 baud**. All devices emit verbose diagnostics — this
is the primary debugging tool, as there is no other instrumentation.

## Architecture

### Communication Protocol

All messages are fixed `char[16]` buffers transmitted over nRF24L01.

| Message | Direction | Meaning |
| --- | --- | --- |
| `PING_<n>` | Button → Display | Discovery probe, repeated every second until adopted |
| `SYSTEM_READY` | Display → Button | Reply to a ping; marks the button ready |
| `<n>` (bare number) | Button → Display | Button press |
| `WIN_<n>` | Display → Button | Winner confirmation, sent to the winning button |
| `GAME_RESET` | Display → All Buttons | New round started; also adopts unconnected buttons |

String constants live in `display.ino` as `MSG_*`. `button.ino` builds its own via
`STR(BUTTON_ID)` macros and uses raw literals for the rest.

### Discovery handshake

Buttons find the display, not the other way round — the display cannot know when a button
powers on. A button pings once a second until it receives `SYSTEM_READY`.

**The nRF24 auto-ACK is deliberately not treated as readiness.** A successful
`radio.write()` only proves the display's *radio* is powered and in RX mode; the ACK is
generated by the chip's state machine with no MCU involvement, so a hung display would keep
ACKing forever and every button would report ready. Only the explicit `SYSTEM_READY` reply,
which can only come from the display's main loop, marks a button ready.

The display adopts buttons **only between rounds** (`handlePing()` checks
`roundInProgress()`). Replying mid-round would put the display into TX and deafen it for a
few milliseconds; a press landing in that window would fail its ACK and be locked out for
the round by the button's one-shot latch. A button that powers up mid-round keeps pinging
and is adopted by the next `GAME_RESET`, which is why `resetForNewGame()` in `button.ino`
also calls `markReady()` — without that, a round started with no button connected would
deadlock permanently (nobody can press, so nobody can win, so the round never ends).

### Radio Addresses

Derived from the player number, not hardcoded:

| Device | Address | Derivation |
| --- | --- | --- |
| Display | `"00001"` | constant |
| Player `n` | `"00002"` + n | `addrFor()` / `snprintf("%05d", n + 2)` |

Radio settings: `RF24_PA_LOW`, `setRetries(5, 15)` = 1500µs delay × 15 attempts ≈ 22.5ms
per failed write. `begin()` enables a 16-bit CRC by default.

Both sketches read on **pipe 0**. This is safe: `openWritingPipe()` overwrites
`RX_ADDR_P0`, but the RF24 library caches the pipe-0 read address and restores it in
`startListening()`. Code that transmits must still re-assert its reading pipe afterwards,
as `sendButtonPress()` and `pingDisplay()` do.

### Changing the player count

`NUM_PLAYERS` in `display.ino` is the single source of truth; addresses and win messages
are computed from the player number. Each button needs a matching unique `BUTTON_ID` in
`0..NUM_PLAYERS - 1`.

**The display hardware caps this at 10.** There is one 74HC595 driving a single digit, so
only `0`..`9` can be shown. `writeDigits()` still takes two bytes for compatibility, but
only the second (`right`) reaches the physical register — the first is shifted through and
discarded. Going past 10 players requires a second shift register and a real two-digit
`showNumber()`.

### Pin Assignments

**button.ino:**
- Pin 2: Button (INPUT_PULLUP, active-LOW)
- Pin 3: Ready LED
- Pin 4: Winner LED
- Pin 5: Connection LED
- Pins 9, 10: nRF24 CE, CSN (SPI)

**display.ino:**
- Pin 2: 74HC595 latch (ST_CP)
- Pin 4: 74HC595 data (DS)
- Pin 5: 74HC595 clock (SH_CP)
- Pin 6: Reset Button (INPUT_PULLUP, active-LOW)
- Pins 9, 10: nRF24 CE, CSN (SPI)

The display has no indicator LEDs; all its output goes to the 7-segment digit.

## Gotchas worth knowing before changing things

**nRF24L01 needs 3.3V, not 5V**, plus a 10–100µF capacitor across VCC/GND close to the
module. Brownout during TX is the usual cause of intermittent `radio.begin()`/`write()`
failures even when the supply voltage is correct.

**`gameActive` is never cleared.** It is set `true` by `resetGame()` and stays true
forever. The predicate for "a round is live" is `roundInProgress()` — `gameActive &&
!winnerChosen`. Gating on `gameActive` alone is a bug.

**Never use `atoi()` on a received message.** It returns `0` for anything unparseable, and
`0` is a valid player number under 0-based numbering, so garbage would be scored as a press
by player 0. Use `parsePlayer()`, which rejects empty strings, non-digits, trailing junk,
leading zeros and out-of-range values. Declined messages are dropped silently — logged to
serial, with no effect on the display — so a stray packet cannot stall the receiver.

**Serial costs real time even with nothing connected.** `Serial.begin(9600)` sets a UART
clock divider; the ATmega328P transmits regardless of whether a host is listening, and
there is no flow control. The TX buffer is 64 bytes and `write()` busy-waits once it is
full, so any burst over 64 bytes blocks at ~1.04ms per additional byte. `resetGame()`
broadcasting to 10 players is the main offender. Unplugging USB changes nothing.

**The display is deaf while transmitting.** Any `sendMessage()` puts it into TX. A press
arriving then gets no ACK and — because `sendButtonPress()` latches `sent = true` on
attempt, not success — that player is locked out for the whole round. This is why junk
handling must not block and why pings are not answered mid-round. The `GAME_RESET`
broadcast in `resetGame()` still has this problem: the display is unreachable for a few
hundred milliseconds after the dashes appear.

**One press per round, by design.** `sent` latches on transmit attempt and only clears on
`GAME_RESET`. The display is the authority on who won; a missed ACK must still lock the
button out, otherwise a retry could arrive after another player has already won.
